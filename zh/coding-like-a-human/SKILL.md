**目标：让用户用最低的理解成本确认方案。**

本文档描述的规则都是启发式规则，并不是强制要求，也没有涵盖你所有应该做或者不应该做的事情，只要能实现这个目标，你可以自由发挥。

要把工作看成连续细化的过程（一层一层减少抽象）：

目标与约束 -> 初步方案（简短文字、图表） -> 代码骨架 -> 局部实现 -> 完整实现

每一轮只细化一层。选择最容易理解的表达方式：能用简短文字、图表讲清楚就写图文；用代码骨架更直观时，就直接修改代码，不要用一两百行文字预先描述几十行（骨架）代码能够更准确表达的设计。

具体工作流程：

1. 计划
  - 检查用户提出的目标和方案，指出风险、不必要的工作及更简单的路线（没有什么是比高效地做一件本不该做的事情更低效的了）
  - 用短段落给出一个或几个初步方案，让用户确认方向；方向确认前只调查和讨论，不修改代码。
  - 新建一份文档来记录最终的草案（尽量不超过50行）。文档格式不强制要求是 MD 文档，如果用 HTML 能让用户更容易理解的话，就用 HTML。
  - 遇到会改变技术路线或使方案不可执行的关键问题时，停下来询问；能够合理推断的内容继续推进，并明确记录假设。
  - 现有代码若存在直接妨碍本任务的边界或职责问题，把必要的整理纳入方案

2. 用户确认最终草案没问题后，搭建骨架（写代码），比如需要哪些类、接口（相当于最终版草案的进一步细化）。
  - “骨架”就是只写类里面有什么字段，必要时写注释说明这些字段是用来干什么的，函数什么的只写输入和输出，函数内部第一行用一句注释大致概括怎么实现这个函数，第二行写`raise NotImplementedError`，不准写任何实现代码。
  - 如果前端和后端都涉及，先把后端骨架搭起来，然后再去搭前端的骨架。
  - 删除不再需要的代码。不要有“每次做完改动后代码都要能跑”的想法，比方说我们要修改某个功能，那就涉及删除已有的一些代码，添加一些代码，这里追求这个代码要能跑完全没有任何意义，因为你这个修改都没有修改完全，其业务逻辑完全是错的，代码能跑也没有价值。
  - 如果一次性搭建完整骨架会超过100行，就按抽象层级分批搭建，先写高层骨架，对于它依赖的下一层组件，用简短的文字描述。停下来等用户读完并确认这一层，再继续搭建下一层。每写完一层就提交一个检查点 commit。

3. 向骨架逐步填入实现和测试（进一步细化），这里通常要把每次代码改动控制在 50~70 行左右，这样才方便用户理解。这里不是强制要求，不要为了遵守行数限制去拆开一个容易理解的结构。每轮改动结束后停下来，等待用户去检查改动，等用户确认后，创建检查点 commit，然后继续。
